## 关键实现决定

1. **composer 是「最后一条 prompt 行」**。真实 Claude / Codex 屏幕里，历史消息也以 `❯` / `›` 开头，只有最后一条是输入框。所有判定都基于这条线：`pending` 看输入区，`delivered` 看输入区上方的 transcript。
2. **`acceptsInput()` 而不是直接用 `idle()`**。Cursor 在任务运行时 composer 仍可用（这正是 `1 task` 跟进队列的来源），如果 `busy()` 一票否决，`queued` 永远不可达。所以 Cursor 的 `busy()` 仍按 spec 认 `1 task` 徽标（供 roster 用），但 `acceptsInput` 对 `followUpQueue: true` 的 CLI 放行。其余 CLI 的 `acceptsInput === idle`。
3. **输入框有草稿时不发**。`idle` 要求 composer 为空，否则 `sendLiteral` 会追加到用户正在写的内容后面。
4. **`dryRun` 返回 `blocked` / `policy`**，detail 写明「would type N chars」。词表里没有 dry-run 专用原因，且 `delivered` 绝不能被伪造；`policy` 是现有词表里最贴近的。
5. **`codex queue` 超时返回 `unverified` / `queue_timeout`**，不是 `blocked`。命令没返回，既不能说没发出去，也不能说已入队；用 `unverified` 还顺带避免了 `index.js` 按 `FALLBACK_REASONS` 回退到 send-keys 造成重复投递。
6. **`foreground_program` 不包含 `node`**。protocols.md 第 2 节写明真实 Codex 窗格的 `pane_current_command` 就是 `node`，把它算成前台程序会让 Codex 的 send-keys 回退永远 blocked。只拦 shell 与编辑器/分页器。
7. **`too_long` 在 4000 字符，`\r\n` 折成空格**，都在任何 tmux 调用之前判断，因此超长消息不会碰目标窗格。
8. **`test/fixtures/fake-cli.js` 在无 TTY 时立即退出**。`node --test` 会把 `test/` 下所有文件当测试文件，包括 fixture；不这样处理 `npm test` 会永久挂起（已实测，见下）。集成测试里 fixture 跑在 tmux 内，stdin 是 TTY，行为不受影响。

## confirm.js 的信号与决定

返回 `'delivered'` 的任一条件：

1. 屏幕出现 `Message from @<fromName>`（Claude 包装行，空白归一后匹配，换行也能命中）；
2. 进入时窗格已 idle，且屏幕已含正文前 60 字符（idle 时 composer 为空，屏幕上的正文不可能是没发出的草稿）；
3. `profile.submitted(baseline, current, text)` 判定为 `delivered` / `queued`（新出现的 transcript 回显、新出现的跟进队列、idle -> busy）；
4. Claude 名册 `sessions/<pid>.json` 的 `status` 从 `idle` 变为非 `idle`。

超时返回 `'pending'`，全程不发任何键。

- **不碰 `cli-profiles.js`**：任务单只允许改 `confirm.js` 与 `test/confirm.test.js`，而 `profileFor()` 只导出 `idle` / `busy` / `prompting` / `acceptsInput` / `submitted`，没有 `promptRe`，拿不到 `transcriptAbove()` 需要的分隔符。所以正文判定改用 profile 自己的 `submitted()`（探针 32 字符），baseline 判定用 `idle()` + 60 字符探针。两者都基于 composer 判断，草稿不会误判为 delivered。
- **baseline 语义**：进入时先抓一屏，已出现包装行或（idle 且正文在屏上）即 `delivered`；否则以这一屏为 `before` 轮询。名册信号要求 `idle -> 非 idle` 的**边沿**，进入时已 busy 不算。
- **读不到屏不猜**：`capturePane` 抛错时该次轮询不产生信号（baseline 直接返回 `pending`），绝不因读不到而报 delivered。名册文件 `ENOENT` 或半写视为未知（其他错误照抛）。

## 集成测试不稳定：两个真实根因

1. **tmux socket 撞名（主因）**。三个 worktree（h1/h2/h3）的 `test/tmux-keys.test.js` 都用 `-L sbb-test`，而每个文件末尾 `after()` 会 `kill-server`。本机同时有多个 agent 跑 `npm test` 时，一个 run 的 kill-server 会删掉另一个 run 正在用的窗格，于是 `capture-pane` 报 `no current target` / `can't find pane: %0`，transport 按 `unverified` / `transport_unavailable` 返回（实测回执：`elapsedMs 2054`、`detail: Command failed: tmux -L sbb-test capture-pane -p -t %0 -S -60\nno current target`）。已改为 `sbb-test-${process.pid}`，每个进程独占自己的 server。
2. **固定 sleep + 单次判定**。负载高时假 CLI 还没回显就被判定为 pending，白花一次补发 Enter。已改为轮询：窗口仍是 2 s（集成测试放宽到 3 s + 3 s），一旦判定非 pending 立即返回，正常路径从 2050 ms 降到 48 ms。

`test/brain-id.test.js` 的 `allocateId increments, pads to 4 and never pads down` 会间歇失败（实测 3 次中 3 次失败、后续 5 次通过，得到 `TST-0003` 而非 `TST-0001`）。根因：`src/registry/brain-id.js:82-105` 的 `maxSeqFromState(tag, opts)` 只把 `opts.sbbDir` 用于 `opts.logPath`，实际扫描的是 `brainsDir()` 与 `receiptLogPath()` 这两个**机器全局**路径。`allocateId({ sbbDir: 临时目录 })` 因此会把全局 receipt log 里的 `TST-000N` 也算进来，测试不隔离，机器上有并发 run 写全局日志时必然抖动。修法：`maxSeqFromState` 用 `brainsDir({ sbbDir: opts.sbbDir })` / 传入 logPath。
