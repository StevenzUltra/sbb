## 关键实现决定

1. **composer 是「最后一条 prompt 行」**。真实 Claude / Codex 屏幕里，历史消息也以 `❯` / `›` 开头，只有最后一条是输入框。所有判定都基于这条线：`pending` 看输入区，`delivered` 看输入区上方的 transcript。
2. **`acceptsInput()` 而不是直接用 `idle()`**。Cursor 在任务运行时 composer 仍可用（这正是 `1 task` 跟进队列的来源），如果 `busy()` 一票否决，`queued` 永远不可达。所以 Cursor 的 `busy()` 仍按 spec 认 `1 task` 徽标（供 roster 用），但 `acceptsInput` 对 `followUpQueue: true` 的 CLI 放行。其余 CLI 的 `acceptsInput === idle`。
3. **输入框有草稿时不发**。`idle` 要求 composer 为空，否则 `sendLiteral` 会追加到用户正在写的内容后面。
4. **`dryRun` 返回 `blocked` / `policy`**，detail 写明「would type N chars」。词表里没有 dry-run 专用原因，且 `delivered` 绝不能被伪造；`policy` 是现有词表里最贴近的。
5. **`codex queue` 超时返回 `unverified` / `queue_timeout`**，不是 `blocked`。命令没返回，既不能说没发出去，也不能说已入队；用 `unverified` 还顺带避免了 `index.js` 按 `FALLBACK_REASONS` 回退到 send-keys 造成重复投递。
6. **`foreground_program` 不包含 `node`**。protocols.md 第 2 节写明真实 Codex 窗格的 `pane_current_command` 就是 `node`，把它算成前台程序会让 Codex 的 send-keys 回退永远 blocked。只拦 shell 与编辑器/分页器。
7. **`too_long` 在 4000 字符，`\r\n` 折成空格**，都在任何 tmux 调用之前判断，因此超长消息不会碰目标窗格。
8. **`test/fixtures/fake-cli.js` 在无 TTY 时立即退出**。`node --test` 会把 `test/` 下所有文件当测试文件，包括 fixture；不这样处理 `npm test` 会永久挂起（已实测，见下）。集成测试里 fixture 跑在 tmux 内，stdin 是 TTY，行为不受影响。

### 2. 验收：`node -e` 打真 tmux 里的假 CLI

```
$ SBB_TMUX_ARGS="-L sbb-test" node --input-type=module -e '...createTmuxKeys().send(...)...'
demo-plain    {"status":"delivered","via":"send-keys","elapsedMs":2054}
  screen: ["› node -e demo message","• node -e demo message","› Ask Codex to do anything"]
demo-swallow  {"status":"delivered","via":"send-keys","elapsedMs":4075}
  screen: ["› node -e demo swallow","• node -e demo swallow","› Ask Codex to do anything"]
```

`demo-swallow` 用了 `--swallow-first-enter`，耗时约两倍 settle（4075 ms ≈ 2 × 2 s），即第一个 Enter 被吞、补发一次 Enter 后 delivered，文字只发了一次。临时 `tmux -L sbb-test` 服务已在测试与脚本结束时 `kill-server`（复查 `no server running`）。

## 与任务单不一致的地方

- **任务单给的窗格号已经过时**：`%29` 现在是 Claude（command `2.1.263`），`%20` 是 Codex（`› Ask Codex to do anything`），机器上当时没有存活的 agy / cursor 窗格。我只读采样了派单允许的 `%30`、`%21`、`%23`、`%20`、`%29`，agy / cursor 的采样来自我自己新建的 `tmux -L sbb-test` scratch 会话（没有向任何真实会话 send-keys）。
- 因此 `agy` / `cursor` 的 **idle** 指纹是实测的，**busy / prompting / queued** 仍是 spec 推导（没有真实进入那些状态的窗格）。

3. **`queue_timeout` 与 `too_long` 是词表新增项**，按任务单要求写进 `docs/spec/receipts.md`；如果 lead 想只保留 `too_long`，`codex-queue.js` 里改成 `blocked` / `transport_unavailable` 即可（但会触发路由回退到 send-keys，有重复投递风险，建议保留 `unverified`）。
