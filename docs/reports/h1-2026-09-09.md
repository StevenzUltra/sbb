### send 的行为

1. 从 `target.claude.keyFile` 读 `peerToken`；文件缺失 / 非 JSON / 无 `peerToken` -> `blocked` + `transport_unavailable`，且不写任何字节。
2. `fromSock` 可接收（`uds:` 前缀 + basename 命中 `SOCK_NAME_RE`）时，先起收件箱再连目标 socket，避免回执早于监听到达。
3. 连接 3 s 超时；失败 -> `blocked` + `socket_connect_failed`。
4. 写 `auth` 行 + `user` 行（`msg_id` / `priority` / `message.content = message.text` / 有 `fromSock` 时带 `from`），然后 `end()`；等写完成回调再判定。
5. 有可接收 `from`：等 `peer_message_status`（按 `orig_msg_id` 过滤），`verifyTimeoutMs` 默认 4000。`delivered` -> `delivered`；`held` / `denied` / `refused` / `dropped` / `expired` -> `blocked` 且 `reason` 同名，`detail` 取 `status_detail`，缺失时取 `drop_reason`；超时 -> `queued`。
6. 无可接收 `from`（缺失或名字不被对端接受）-> 写完即 `queued`，不等待。
7. 结果为 `delivered` / `queued` 且 `opts.notifyIdle` 为真时，在新连接上重发 `auth` 后发 `notify_when_idle`（`from_mode` 默认 `bypass`）。该帧失败只追加到 `receipt.detail`，不改变已定状态。

## PR #1 审阅后的修正（2026-09-09）

### 第二轮：fromSock 不可接收一律 blocked

发起方决定：`fromSock` 名字不匹配 `SOCK_NAME_RE` 也归为调用方配置错误，不得报成排队。现行为：

- `fromSock` 缺失 -> 写完即 `queued`（不变）。
- `fromSock` 有值但不是 `uds:` 地址 -> `blocked` + `transport_unavailable`，`detail` 为 `fromSock must be a uds: address: <值>`，不写字节。
- `fromSock` 是 `uds:` 但 basename 不匹配 `SOCK_NAME_RE` -> `blocked` + `transport_unavailable`，`detail` 为 `fromSock name not receivable by peers: <name>`，不写字节。
- `fromSock` 合法但不是本进程收件箱 -> `blocked` + `transport_unavailable`，`detail` 为 `fromSock must be this process inbox: <inbox.sockPath>`（第一轮修正）。

非 `uds:` 前缀与名字不匹配分成两条不同 `detail`，因为前者名字本身可能合法，只是地址形式不对；发起方若要求统一措辞请示下。用例：`a fromSock whose name peers would ignore is blocked before any write`、`a fromSock that is not a uds: address is blocked before any write`。

### 第一轮：fromSock 必须等于本进程收件箱

发起方审阅指出：`send()` 在 `from.receivable` 时按 `dirname(from.path)` 起收件箱，收件箱实际监听 `<dir>/<进程 pid>.sock`，但没有校验 `from.path` 是否等于 `inbox.sockPath`。调用方传 `uds:/tmp/cc-socks/999.sock` 这类合法名字时，回执永远到不了本进程，结果恒为 `queued`，等于把调用方错误报成了排队。

修正：拿到 inbox（含 `opts.inbox`）后校验 `from.path !== inbox.sockPath` -> `blocked` + `transport_unavailable`，`detail` 为 `fromSock must be this process inbox: <inbox.sockPath>`，且不写任何字节。新增 2 个用例：合法但非本进程的 socket 名、`opts.inbox` 指向另一路径。

## 追加任务：`<cross-session-message>` 包装（2026-09-09）

背景见 main `d242309` 新增的 `docs/spec/protocols.md` 第 1 节实测表（`from` 指向发送进程自己的 socket 才不 held；包装后显示为 `Message from @<名字>: …`）。实现位于 `buildContent()`：

- `message.fromName` 缺失 -> 纯文本（`from` 有值时仍带 `from`）。
- `fromName` 存在且 `from` 可接收 -> `content` 包成 `<cross-session-message from="<fromSock>" from-name="<名字>"[ from-mode="bypass|prompting"]>\n<body>\n</cross-session-message>`，属性顺序 `from`、`from-name`、`from-mode`。
- `from-mode` 只在 `message.fromMode` 恰为 `bypass` / `prompting` 时写入，其它值按规格「未知的省略」处理。
- `from-name` 含 `"`、`<`、`>` 或换行 -> 退回纯文本，`receipt.detail` 注明 `content not wrapped: from-name has forbidden characters: <名字>`。
- `from` 值含 `[A-Za-z0-9%:_/.\-]` 之外的字符 -> 退回纯文本，`detail` 注明 `content not wrapped: fromSock has characters peers reject: <值>`。
- `fromName` 存在但 `from` 不可接收（无 `fromSock`）-> 纯文本，`detail` 注明 `content not wrapped: no receivable fromSock`。这一条超出追加任务的原话（只列了「缺失」「可接收」两种），加注是因为静默降级会让发送方以为对方看到 `Message from @名字`，请发起方确认是否保留。

用例：`wraps the body as cross-session-message when fromName is present`（逐字节）、`omits from-mode when the sender mode is unknown`、`keeps plain content when fromName is missing`、`falls back to plain content when from-name contains ...`（引号 / 尖括号 / 换行三条）、`notes that fromName cannot be wrapped without a fromSock`。

注：`src/types.js` 的 `OutboundMessage.text` 注释仍写「Transports never rewrite text」，而本包装要求传输改写 `content`（`fromName` 的新注释已写「uds wraps the body with it」）。按发起方指令实现，未改 `types.js`（不属本任务文件）。

## 追加：user 帧的 `reply_to`（2026-09-09）

发起方要求：`message.replyTo` 存在时在 uds 的 `user` 帧加 `"reply_to": <msgId>`，缺失不写。

实现：`userLine()` 在 `priority` 之后、`from` 之前写入该字段，仅当 `message.replyTo` 为真。字段名与接收端一致——`src/cli/util.js:153` 读 `frame?.reply_to ?? frame?.replyTo`，`test/delivery.test.js:223` 也按 `reply_to` 断言，属 h3 已约定的线上契约。

用例：`adds reply_to to the user frame when the message replies to a msgId`（逐字节，含 `reply_to` 与 `from` 同帧）、`omits reply_to when the message has none`。

## 与规格的差异和补充（请复核）

1. **`socket_connect_failed` vs `transport_unavailable`**：`docs/spec/protocols.md` 状态映射表把「socket 缺失 / 连接被拒」归为 `transport_unavailable`，任务单第 2 条写的是 `socket_connect_failed`。按任务单实现。两者都在 `transports/index.js` 的 `FALLBACK_REASONS` 里，路由回退行为一致。
2. **未知对端状态**：状态表未覆盖的状态值（例如对端将来新增）映射为 `queued`，原始值写进 `detail`（`unknown peer status: <x>`）。理由：socket 已接受消息，不能谎报 `delivered`，也不该按 `held` 一类终态阻断。规格若要求别的映射请指明。
3. **`fromSock` 不可接收时**：`blocked` + `transport_unavailable`（见上节 PR #1 审阅后的修正），不再空等 4 s，也不报成 `queued`。
4. **收件箱 API 增补 `off(event, fn)`**：任务单只列了 `on`，但 `send` 等回执时必须在超时/命中后解绑监听，否则长驻收件箱上的监听器会随发送次数增长。`claudeUds` 另导出 `closeInboxes()`，用于 CLI 退出与测试回收惰性启动的收件箱。
5. **收件箱 `error` 事件**：socket 层错误与无法解析的行都发 `error`（不吞）。没有监听者时按 Node 惯例抛出，属于有意为之的「响亮失败」，若希望静默丢弃请说明。
6. **`dryRun` 未实现**：`SendOptions` 里有该字段，但任务单未列入本传输的交付物，当前由调用方在进入 `send` 前处理。
7. **`<cross-session-message>` 包装未实现**：按任务单备注，只发纯文本 `content`。
8. **测试文件名副作用**：Node 26 默认测试 glob 会把 `test/fixtures/fake-claude-server.js` 也当一个测试文件加载（0 用例、通过）。不影响结果，如需干净可加 `--test-skip-pattern` 或把 fixture 移出 `test/`；但任务单固定了该路径，故保留。
