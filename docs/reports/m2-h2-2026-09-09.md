## 关键实现决定

1. **规划是纯函数**。`planMove(brainRef, targetRef, { getBrain, listBrains, rows })` 只读注入的注册表，环、no-op、目标存活三类检查都返回结构化的 `checks`，CLI 据此选退出码，因此不需要 tmux / socket / 真实 `~/.sbb` 就能测。
2. **`target_live` 只在给了 `rows` 时检查**。单测和库调用可以省略；CLI 传 `roster({ withStatus: false })`，判定为 `rows.some(r => r.brainId === parent.id && r.paneId !== null && r.status !== 'stale')`。
3. **`applyMove` 与清标记是一次写入**。`{ ...brain, parent, role }` 后 `delete updated.pendingMove`，再交给 `saveBrain` 的原子写，避免「改完上级还留着 pendingMove」的中间态。
4. **`waitIdle` 两条判定链**。Claude 走 `readClaudeStatus`（构造一个只含 `claude.pid` 的合成 target 读 `sessions/<pid>.json`）；其余 CLI 走 `capturePane` + `profileFor(cli).idle()` 指纹。进入等待前先写 `pendingMove`，判到 idle 后清掉；超时保留标记并返回 `{ status: 'timeout' }`。
5. **`--handoff` 用「ask 成功或文件非空」判定**。见下面的实测发现：真实 Claude 会在自己窗格里回答而不走 sbb 回复通道，`sbb ask` 因此耗尽 10 分钟并以 5 退出，但摘要文件已经写好。`requestHandoff` 因此同时返回 `ok`（ask 退出码 0）和 `wrote`（文件非空），CLI 取 `ok || wrote` 决定是否把路径写进通知。
6. **`notify` 三条消息按 spec 顺序**（原上级 → 新上级（root 时跳过）→ 该脑自身），每条独立投递并收集回执；某条 `blocked` 只打印、不回滚已完成的 move。角色标签沿用 `identity.brain ? identity.role : ROLE_LABELS.user`，所以从命令行发起时是「用户」。
7. **`ls` 的提示放进 `statusCell`**。合并 `origin/main` 时 `toCells` 与 `printTree` 都改用了新抽出的 `statusCell(row)`，把 pending 提示写在 `statusCell` 内部，既满足「只改一个函数」，也顺带让 `--tree` 视图一致。
8. **退出码**：环 / 未知目标 / 目标不存活 → 4（`blocked`，原因 `policy` 或 `target_not_found`）；已在目标下 → 0 并打印 `nothing to do: …`；等待超时 → 5，stderr 提示 `sbb move <name> --to <to> --now` 续做。

**C. `--handoff`（两次真实运行）**

1. **`--handoff` 在「brain 只在窗格内作答」时会白等满 10 分钟**（实测 10:16）。摘要文件仍会被采纳，代价只是时间。spec 写死 `--wait 10m`，我没有改等待时长；若要缩短，需要 spec 层决定（例如 `--handoff-wait` 或轮询文件出现）。
2. **非 Claude 的 `waitIdle` 只有单测证据**。真实 scratch 里没有 codex / agy / cursor 脑可用，指纹判定用 `test/fixtures/move/screens.json` 覆盖；Claude 路径是真实点验的。
3. **副作用**：两次真实验收各让 Claude 对当时那个临时目录弹了一次信任确认，`~/.ai-account-a/claude.json` 的信任列表里因此留下两条已删除目录的条目（需要时手工删掉即可）。
